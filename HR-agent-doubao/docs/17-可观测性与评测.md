# 17 · 可观测性与评测：没有评测就没有迭代

## 17.1 本章目标

1. 用 `BaseCallbackHandler` 采集每次模型/工具调用的耗时与 token；
2. 用 Golden Case 做回归，并区分 v1（合格）与 v2（退步）；
3. 四个必看指标：任务成功率、工具准确率、幻觉率、成本/P95；
4. 知道 Trace 该记什么、不该记什么（隐私）。

跑法：`python ch17_observability/main.py`

## 17.2 埋点：`BaseCallbackHandler`

```python
class Tracer(BaseCallbackHandler):
    def on_llm_start(self, *a, **kw):  self.stack.append({"kind": "llm",  "t0": time.time()})
    def on_llm_end(self, *a, **kw):    self.spans.append({**自, "ms": ...})
    def on_tool_start(self, *a, **kw): ...
    def on_tool_end(self, *a, **kw):   ...
```

接进去：

```python
agent.invoke({"messages": [...]}, config={"callbacks": [tracer]})
```

实测：

```
  span 记录：
    {'kind': 'llm',  'ms': 0.2, 'tokens': 0}
    {'kind': 'tool', 'ms': 0.1}
  汇总：llm_calls=3, tool_calls=2, total_ms=0.3
```

★ 一个 span 至少记六样：**谁（node/工具名）、什么时候、多久、多少 token、成功没、输入摘要（脱敏）**。少一样，出事时都查不下去。

生产上直接用 **LangSmith**：

```python
import os
os.environ["LANGCHAIN_TRACING_V2"] = "true"
os.environ["LANGCHAIN_API_KEY"] = "..."
os.environ["LANGCHAIN_PROJECT"] = "hr-agent"
```

不用写任何埋点代码，每次 `invoke` 自动上报。但**仍要知道 span 里该有什么**，否则你看的是一堆看不懂的瀑布图。

## 17.3 Golden Case：三到五条起步就够

```python
GOLDEN = [
    {"id": "leave_balance",
     "q": "张伟 2026 年还剩几天年假",
     "must_call": "get_leave_balance",
     "bad": ["我无法查询", "请自行登录"],
     "must_contain": ["7 天"],
     "cite": "leave_bal"},
    ...
]
```

一条 case 至少四个字段：

| 字段 | 判断什么 |
|---|---|
| `must_call` | 该调的工具调了没（工具准确率） |
| `must_contain` | 关键事实说对没（正确性） |
| `bad` | 有没有出现"我不知道""请自己查"这类废话（可用性） |
| `cite` | 有没有给出处（可追溯性） |

## 17.4 一个真实的坑：剧本被消费完了

最初三个 case 共用一份可消费的剧本列表，结果全部返回第一条答案：

```
  v1 通过率：0/3
```

原因：`FakeMessagesListChatModel` 的剧本是**有状态、会被消费**的。改法：每个 case 按版本现场生成独立剧本：

```python
def build_script(case, version):
    return [ai_tool(case["must_call"], case["args"]),
            ai_text("..." if version == "v1" else "我无法查询，请自行登录")]
```

实测：

```
  v1 通过率： 3/3 = 100%
  v2 通过率： 0/3 = 0%
  ★ 同一批 case，两种版本，一个通过一个挂 —— 这才叫回归测试
```

★ 教训：**评测脚本本身要能被信任。** 评测全部失败时，先怀疑评测，再怀疑 Agent。

## 17.5 四个指标 + 三个百分位

| 指标 | 怎么算 | 目标 |
|---|---|---|
| 任务成功率 | Golden 通过数 / 总数 | ≥ 90%（核心流程） |
| 工具调用准确率 | `must_call` 命中率 | ≥ 95% |
| 幻觉率 | evidence 对不上 / 总数（第 02 章） | < 3% |
| 成本 | 每任务 token × 单价 | 按业务定 |
| P50/P95/P99 延迟 | span 的 `ms` 分布 | P95 < 3s（对话型） |

**只报平均值是最常见的自欺**：P50 好看、P99 是 20 秒，用户体验照样崩。

## 17.6 Bad Case → 回归用例的闭环

```
线上发现 bad case → 脱敏 → 写成 GOLDEN 一条 → 每次改动跑回归 → 不红才发
```

这一步把"感觉变好了"变成"数字没退步"。没有这个闭环，Agent 项目就是"每次改 prompt 像抽奖"。

## 17.7 Trace 的隐私红线

| 该记 | 不记（或脱敏） |
|---|---|
| 工具名、耗时、token 数 | 身份证、银行卡、完整薪资 |
| 输入摘要（截断 + 打码） | 完整简历原文 |
| 错误类型 | 用户手机号、住址 |
| `user_id` 的哈希 | 真实 `user_id` |

★ Trace 系统本身是最大的数据泄露面：三年日志全带身份证，等于把全公司信息存了一份。

## 17.8 常见坑

1. **只记成功路径**：失败/重试不记，出事时完全瞎。
2. **评测用线上真实数据**：既不合规，也不稳定（数据会变）。
3. **Golden 用例只有 1 条**：改 A 过、改 B 挂，你在两个用例间反复横跳。
4. **上线后不跑回归**：模型厂商升级一次，全站悄悄退化。
5. **把"用户满意度"当唯一指标**：用户点"有帮助"不代表答对了（第 02 章的 evidence 才是硬指标）。
