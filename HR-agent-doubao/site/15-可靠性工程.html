15 · 可靠性工程：重试、超时、降级、幂等、熔断

15.1 本章目标

把"能跑通"变成"敢上线"。五个手段各有分工，别混：

手段回答的问题LangChain 原语 / 自写
重试这次失败可不可以再试一次？runnable.with_retry(...)
超时等多久该放弃？自包 asyncio.wait_for
降级放弃之后用什么代替？runnable.with_fallbacks([...])
幂等重发了会不会写两条？自写幂等键
熔断连续失败到多少就别再试？自写 breaker

跑法：python ch15_reliability/main.py

15.2 重试：with_retry

chain = RunnableLambda(flaky).with_retry(stop_after_attempt=3, wait_exponential_jitter=True)

实测：

  结果：成功（第 3 次尝试）
  不可重试错误：参数非法：emp_id 格式不对（这类错误重试 3 次只是浪费钱）

★ 只对"瞬时故障"重试：超时、502、限流、连接断开。

一律不重试的：参数校验失败、权限错误、业务规则拒绝（余额不足、超带宽）。 对它们重试，等于把一次用户错误放大成三次成本 + 三次延迟。

15.3 超时：LCEL 不带，必须自己包

async def with_timeout(x, seconds):
    try:
        return await asyncio.wait_for(slow(x), timeout=seconds)
    except asyncio.TimeoutError:
        return "⛔ 超时，已放弃并转兜底"

实测：1.0s 上限 → 超时放弃 / 5.0s 上限 → 迟到的答案。

三个层级都要有超时：

  1. 单次模型调用（通常 30–60s）
  2. 单个工具调用（通常 5–10s，写操作 15s）
  3. 整个任务（按 SLA 定，超时就转人工）

15.4 降级：with_fallbacks

chain = primary.with_fallbacks([backup_model, rule_based])

实测：主模型抛 500 → 备模型接住（备模型接住了）。

降级的三个层次（越往下越便宜、越稳、越难看）：

  1. 换模型（同厂商另一区域/另一版本）
  2. 换小模型（复杂推理 → 简单抽取）
  3. 退化为规则/固定话术（"请到 OA 自助查询"）—— 必须有这一层

第 3 层是最多人漏的。没有它，模型全挂时你的 Agent 就是 500 页面。

15.5 幂等：重发三次只能有一条记录

class IdempotentWriter:
    def submit(self, idem_key, payload):
        if idem_key in self.records:
            return f"命中幂等键，返回已有记录 {self.records[idem_key]['id']}"
        ...

实测：

  第 1 次提交 → 新建记录 R1
  第 2 次提交 → 命中幂等键，返回已有记录 R1
  第 3 次提交 → 命中幂等键，返回已有记录 R1
  尝试 3 次，实际记录 1 条

★ 幂等键要由业务语义拼：谁 + 什么事 + 哪个时间点。

leave:E1001:2026-12-01:年假
offer:K1001:v3

用随机 UUID 做键，等于没有幂等（每次重发都是新键）。

真实场景：网络超时后"重发"，你不知道第一次到底成功没有——幂等键是唯一能让你安全重发的机制。

15.6 熔断

class Breaker:
    def call(self, fn):
        if time.time() < self.open_at:
            return "⛔ 熔断中，直接返回兜底（不再调用下游）"
        ...

实测：

    第 1 次：失败（累计 1）
    第 2 次：失败（累计 2）
    第 3 次：失败（累计 3）
    第 4 次：⛔ 熔断中（不再调用下游）
    第 5 次：⛔ 熔断中

熔断保护的是下游和你的预算。没有它，一个挂掉的薪酬系统会被你的重试打穿。

15.7 一张决策表

现象该做什么
偶发 502、连接超时重试（最多 3 次，指数退避）
参数错误、权限拒绝不重试，直接返回用户
慢但最终会成功提高超时，或改异步任务（第 16 章）
主模型不稳降级链
全挂规则兜底 + 告知用户"稍后再试"
重复提交幂等键
下游持续失败熔断 + 告警

15.8 常见坑

  1. 对业务错误重试：余额不足重试三次还是不足，只是让用户多等 9 秒。
  2. 重试没有退避：瞬间三次请求打过去，把限流打成封禁。
  3. with_retry 包在整条 Agent 上：整条重跑会重复执行工具（写操作就出事了）。只包"单次调用"，幂等靠键。
  4. 超时值 > 上游超时：你的 30s 超时毫无意义，因为调用方 10s 就断了。
  5. 降级链里没有规则兜底：全模型挂了直接白屏。
  6. 幂等键用了 UUID。

15.10 练习

  1. 把 stop_after_attempt 改成 1，观察 flaky 直接失败——这就是"不重试"的代价。
  2. 给 Breaker 加 half-open 状态：冷却后放一个请求试探。
  3. 把幂等键存到 sqlite，进程重启后验证仍然去重。
