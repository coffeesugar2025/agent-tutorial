08 · Context Engineering：Token 预算、裁剪、压缩

8.1 本章目标

  1. 会算 token 预算（无 Key 也能算）；
  2. 用 trim_messages 有规则地裁剪：保 system、保最近、不留下"孤儿"消息；
  3. 用摘要压缩把旧对话压成"事实清单"；
  4. 知道六种压缩手段的适用场景，以及"什么不放进上下文"才是最狠的一招。

跑法：python ch08_context/main.py

8.2 先算预算

def count_tokens(messages) -> int:
    # 中文约 1 字 ≈ 1 token，英文约 4 字符 ≈ 1 token
    ...

真实项目用 tiktoken（本环境已装），但粗估就够做预算决策——你要的是"什么时候该压"，不是精确计费。

实测：20 条消息 ≈ 436 tokens，单条最长 29 tokens。所以"上下文爆炸"通常是条数问题，不是单条长度问题。

8.3 trim_messages：三个开关决定裁完还能不能用

trimmed = trim_messages(
    msgs,
    max_tokens=220,
    strategy="last",            # 从最新往前留
    token_counter=count_tokens,
    include_system=True,        # ★ system 永远保
    start_on="human",           # ★ 裁完不能以 AI/Tool 开头
    allow_partial=False,
)
  • include_system=True：不然模型丢了"不许编造"这条，后面全靠猜。
  • start_on="human"：很多模型要求第一条是 user；裁完以 ToolMessage 开头会直接 400。
  • strategy="last" vs "first"：对话场景用 last；长文档分析场景用 first（前文是任务描述）。

实测输出（很值得看）：

  预算 220 → 剩余 9 条，约 211 tokens
    [System] 你是招聘助手…
    [Human] 再帮我看看第 4 个候选人的情况…
    [Human] 再帮我看看第 5 个候选人的情况…
    ...

注意：早期那几条工具结果（张伟/带宽/特批流程）被裁掉了，留下的是一串同质化的重复提问。 这就是"纯截断"的根本问题：它按位置裁，不按价值裁。所以需要下面的摘要压缩。

8.4 摘要压缩：压事实，不压标点

SUMMARIZE = ChatPromptTemplate.from_messages([
    ("system", "把下面的对话压成不超过 80 字的事实清单。只保留：已确认的数据、已做的决定、待办。"
               "丢掉寒暄、重复、模型的解释过程。"),
    ("human", "{history}"),
])
summary = (SUMMARIZE | model).invoke({"history": flat}).content

实测：

  压缩前 156 tokens → 压缩后 55 tokens
  摘要：已确认：P1001 高级前端，带宽 22-25K；C1001 张伟，技术中心，一面通过，
        期望 28K 超带宽 3K。待办：走薪酬特批（HRBP 发起→薪酬审批→HRD 确认）。
  重建后的上下文：4 条 / 132 tokens

摘要必须保留三类东西：数字、决定、待办。只写"用户询问了年假政策，助手进行了回答"的摘要，等于把上下文压成了噪声。

8.5 六种压缩手段（按信息损失从低到高）

手段具体做法什么时候用
工具结果瘦身ToolMessage 只留用到的字段永远，优先做
检索按需只塞命中的 2 段，不塞整篇 SOPRAG 场景必做
去重合并同一事实出现 5 次留 1 次长会话
结构化抽取50 条消息 → 一张 {字段:值} 表任务型对话最划算
摘要压缩旧对话 → 事实清单超过 10 轮启动
截断只留最近 N 条兜底，慎用

工具结果瘦身还顺手解决了安全问题：

    工具结果：43 → 22 tokens（同时把敏感字段挡在模型之外）

原始工具返回里有 id_card、bank、salary——模型看到就等于泄露风险。瘦身不只是省钱，是权限控制。

8.6 水位线：别等爆了再压

def water_level(used, limit):
    r = used / limit
    if r < 0.6:  return "🟢 正常：全量保留"
    if r < 0.85: return "🟡 预警：启动结构化抽取 / 检索按需"
    return "🔴 危险：强制摘要压缩 + 外置状态，并告诉用户'我需要重新确认一下'"

最后一句很重要：压缩会丢信息，丢信息时要说出来。"我需要重新确认一下您刚才提到的城市"比默默答错强得多。

8.7 最狠的一招：决定什么不放进上下文

  • 计划、待办、已执行步骤 → 放 LangGraph state / 数据库，按需取摘要
  • 大文档 → 放向量库，按需检索两段
  • 长工具输出 → 放文件/对象存储，只回填"结果 + 关键字段"

★ 上下文工程的核心不是压缩技巧，是"什么不进上下文"。 一个 200 行的工具输出，从头就不该进 prompt。

8.8 常见坑

  1. max_tokens 当字符数：trim_messages 的 max_tokens 走你给的 token_counter，别混用字符数函数。
  2. 裁完不留余地：裁剪到刚好 220/220，下一轮再加一条就爆。留 20% 余量。
  3. 摘要每轮都做：成本翻倍。按水位线触发（比如每 5 轮或超过 60%）。
  4. 摘要后不保留原始：用户追问细节时无法回溯。摘要 + 原始落库，两者都要。
  5. 忘了 system 里也可能有敏感信息：system 塞了完整制度文档，等于每轮都在泄露。

8.10 练习

  1. 把 count_tokens 换成 tiktoken（cl100k_base），对比估算误差。
  2. 用 max_tokens=120 裁一次，看早期"不许编造"的约束是否被裁掉，以及后果。
  3. 写一个"每 5 轮自动摘要"的循环，观察摘要里最先丢的是哪类信息（通常是具体数字）。
