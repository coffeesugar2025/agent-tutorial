## 一、主推版（推荐）

### 某电商平台 · 智能导购与售后 Agent 平台

**角色**：Agent 平台核心开发（后端负责人）　**团队**：〔待填，例：5 人 / 2 后端 + 1 前端 + 1 算法 + 1 测试〕　**时间**：〔待填〕
**技术栈**：Java 17 + Spring Boot 3 + LangChain4j / Python 3.12 + FastAPI + LangChain / Vue3 + TypeScript / MySQL · Redis · RabbitMQ · Milvus

**项目背景**
平台售前咨询与售后政策问答高度重复、人工客服成本高。项目目标是让 AI 承接标准化咨询（导购推荐、订单物流、退换货政策），复杂问题与高风险操作转人工；退款等资金类操作必须保留人工审批，不能由模型直接执行。

**职责与产出**

- **Agent 运行时（核心 owner）**：主导 Supervisor + 3 个子 Agent（导购 / 客服 / 运营）的分派架构，确定"路由只发生一次、子 Agent 内部闭环"的原则，规避多 Agent 互调带来的错误传播与成本放大；定义 10 类 SSE 事件协议（`meta/agent/delta/tool_call/tool_result/citation/approval/usage/done/error`），作为前后端联调的唯一接口约定。
- **工具治理体系**：把工具抽象为「读 / 写 / 不可逆」三级风险模型——READ 可重试、WRITE 幂等 + 审计、IRREVERSIBLE 强制人工审批；统一封装超时、指数退避、幂等键、审计与链路埋点，业务方新增工具只需声明式注册。当前接入 12 个工具，覆盖商品、订单、物流、售后、知识检索与经营分析。
- **可控性设计**：实现 7 条终止策略（超时 / 步数 / Token 预算 / 无进展 / 重复调用 / 待审批 / 正常结束）。其中"连续两步信息摘要相同""同工具同参数连续两次"两条专门治理大模型的礼貌性空转，并用 20+ 单测锁定判定优先级，避免多条同时命中时行为漂移。
- **RAG 检索链路**：负责文档解析、递归+语义切片与父子块策略、dense(1024) + 稀疏(BM25-lite) 双路召回、RRF 融合、LLM 重排与上下文预算组装；**权限过滤下推到检索前**，避免越权召回；设计 Milvus → MySQL 全文 → 内存 三级降级，检索侧故障不阻断对话主链路。
- **多模型接入与成本治理**：统一接入 DeepSeek / 通义千问 / OpenAI / Ollama 四家供应商，按任务类型分级路由 + 失败级联 + 熔断（连续 3 次失败 / 冷却 30s）+ 成本核算到"每成功任务成本"；推动上线 Mock 模式，使 CI 与联调不依赖真实 Key、不产生费用。
- **Human-in-the-loop 闭环**：落地审批单状态机（`PENDING → APPROVED / REJECTED / EXPIRED`）、申请人本人与客服坐席双通道鉴权、审批通过后经 MQ 异步执行且幂等，并补齐超时失效与审计留痕。
- **可观测与稳定性**：建设 trace / span 体系（LLM、TOOL、RETRIEVAL、AGENT、GUARDRAIL 五类），接入 Prometheus 指标与成本看板，支持基于 checkpoint 的轨迹重放；推动灰度发布与降级预案落地。
- **跨端协作**：主导 API 契约与数据库设计，Java 端与前端按契约并行开发；用「契约文档 + 共用 DDL + 枚举硬编码 + 契约测试」四道锁保证双端一致，降低联调返工。

**项目成果**

- 平台已覆盖导购、售后、经营分析三条业务线，累计 〔待填：日均会话数 / 覆盖咨询占比〕。
- 稳定性：接口 P95 延迟 〔待填〕ms，降级预案触发 〔待填〕 次且未造成用户侧不可用；资金类操作 100% 走人工审批，零越权执行。
- 工程沉淀：339 个代码文件 / 约 3.6 万行代码，126 个自动化测试（全 Mock、零外部依赖），9 个服务一键编排，形成可复用的 Agent 平台底座，后续业务接入成本从 〔待填〕 降至 〔待填〕。

## 六、面试追问预案（公司项目版）

**Q1：你在团队里具体负责哪部分？**
> 我负责 Agent 运行时和工具治理这一层——循环、终止策略、工具的风险分级与审批中断；RAG 的切片和召回策略也是我做的。前端和 Java 端是按我定的契约并行开发的，运维的部署编排是另一位同事。

**Q2：为什么既有 Java 又有 Python 两套后端？**
> 〔按真实原因答，常见三种〕
> - **存量栈原因**：主站是 Java，Agent 能力先由算法团队用 Python 验证，稳定后需要并入 Java 体系，所以先保证契约一致、双端可切换。
> - **能力分工**：Python 侧离模型和检索生态近、迭代快；Java 侧承接交易域、权限与审计更成熟。
> - **迁移过渡**：一期双端并行做灰度对比，二期收敛到一套。
> 代价我也清楚：工具调用协议不同导致 prompt 无法共用、评测集字段不一致导致数据集不能共用。如果重来我会直接收敛到一套。

**Q3：怎么保证模型不乱调工具、尤其不乱退款？**
> 三道闸：①工具按风险分级，`IRREVERSIBLE` 的工具函数体**只负责抛审批信号**，不做任何副作用；②审批单独立存储，跨请求存活，通过后才由 MQ 异步执行真正的落库函数；③执行侧用幂等键 + 唯一索引兜底，重复执行不会重复退款。

**Q4：怎么防止 Agent 死循环烧钱？**
> 7 条终止条件，硬的（步数/Token/超时）只是兜底，真正管用的是两条软的：每步产出一个信息摘要做哈希，连续两步相同就停；同工具同参数连续两次也停。判定**顺序固定**，否则多条同时命中时结果不稳定，为此写了专门的优先级单测。

**Q5：上线后出过什么问题？**（这题最能区分真假，务必讲真实故障）
> 举一个真实的即可，例如：① 检索服务抖动时未及时降级，导致回答质量下降；② 某次 prompt 改动后工具调用率异常；③ 成本突增（长会话累积上下文）。
> 重点讲**怎么发现（trace/指标）→ 怎么定位（span 逐层看）→ 怎么修（降级/回滚/加预算）→ 怎么防复发（加告警/加用例）**。

**Q6：RAG 效果怎么评估、怎么迭代？**
> 分三层：检索层 recall@k / nDCG / MRR，上下文层看喂进去的对不对，生成层看 faithfulness。先定位再优化——recall 高但 nDCG 低是排序问题该调重排，recall 低是切片或查询改写问题。相关性标注成本高，我只对核心政策文档做了人工标注，其余用规则断言 + 抽样人工复核。

**Q7：成本和延迟怎么优化的？有数据吗？**
> 成本侧：短任务（路由、重排）走 fast 模型，prompt 做稳定前缀布局提缓存命中，按任务设 token 预算。延迟侧：SSE 流式先把首 token 推出去。
> 〔如果有数据就报：单会话成本从 __ 降至 __；P95 从 __ 降至 __〕。**没有数据就说没有**——"我们建了埋点但还没做对比实验"是完全可以接受的回答。

**Q8：这个项目你觉得最大的不足？**
> ① 评测只做到单元+集成，契约比对和性能压测脚本没落地，"质量闭环"没闭上；② 训练侧完全没碰，能力天花板受限于通用模型；③ 双后端维护成本高，长期看应该收敛。
