## 项目经历

### 具体内容

智能导购与售后 Agent 平台
【角色】：
Agent 平台核心开发（后端负责人）
【项目背景】：
平台售前咨询与售后政策问答高度重复、人工客服成本高。
目标是让 AI 承接标准化咨询（导购推荐、订单物流、退换货政策），
复杂问题与高风险操作转人工；退款等资金类操作必须保留人工审批，
不能由模型直接执行。
【技术栈】
前端：Vue3 
后端：Python + FastAPI + LangChain /LangGraph 
数据库：MySQL 、Redis · 
消息队列：RabbitMQ · 
RAG：Milvus
部署：AWS/Docker/K8s
【职责与产出】
1，Agent 运行时：
主导 Supervisor + 3 个子 Agent（导购/客服/运营）分派架构，确立"路由只发生一次、子 Agent 内部闭环"原则。
2，工具治理体系：
抽象「读/写/不可逆」三级风险模型——READ 可重试、WRITE 幂等+审计、IRREVERSIBLE 强制人工审批；统一封装超时、指数退避、幂等键、审计与埋点，业务方新增工具只需声明式注册。
3，可控性设计：
实现 7 条终止策略（超时/步数/Token 预算/无进展/重复调用/待审批/正常结束）。
4，RAG 检索链路：
负责解析、递归+语义切片与父子块、dense(1024)+稀疏(BM25-lite) 双路召回、RRF 融合、LLM 重排与上下文预算组装；权限过滤下推到检索前；设计 Milvus → MySQL 全文 → 内存 三级降级。
5，多模型接入与成本治理：
统一接入 DeepSeek/通义千问/OpenAI/Ollama，按任务分级路由 + 失败级联 + 熔断 + 归因到"每成功任务成本"；推动 Mock 模式上线，使 CI 与联调不依赖真实 Key、不产生费用。
6，HITL 闭环：
落地审批状态机、申请人本人与客服坐席双通道鉴权、审批通过后经 MQ 异步执行且幂等，补齐超时失效与审计留痕。
7，可观测与稳定性：
建设 trace/span 体系（LLM/TOOL/RETRIEVAL/AGENT/GUARDRAIL 五类），接入 Prometheus 与成本看板，支持基于 checkpoint 的轨迹重放；推动灰度发布与降级预案落地。
