# Agent 工程能力覆盖矩阵 · 审计与扩展实现

> 对照清单：Agent 工程化 12 项 + RAG 与知识工程三层 + LLM 与模型工程 + 5 条横向要求。
> 本轮结论：**原有覆盖 10 项、本轮新增实现 30 项、适配器契约 4 类、明确不适用 1 类**。
> 全部新增能力落在 `backend/app/capabilities/` 与 `backend/app/api/routes_ext.py`（`/v2/*` 共 37 个端点），
> 配套 `backend/tests/test_extended_capabilities.py` **95 个新用例**，后端全量 **192 passed**。

哪些是真实代码、哪些只是适配器契约、哪些根本不该在这个仓库里做。

## 八、必须说清的四个边界

1. **HashEmbedding 不是语义向量**：它是确定性哈希特征，用于验证「切片→向量化→召回→重排→引用」整条工程链路；
   生产替换为 BGE / OpenAI Embedding 时只需保持 `embed(text) -> vector` 接口。
2. **Sandbox 是 AST 表达式级，不是 OS 隔离**：禁 import / 属性 / 赋值 / 循环 / 任意调用 + 空 builtins；
   真正执行不可信代码仍需容器 / gVisor / seccomp，模块里已明确标注。
3. **外部向量库与 Neo4j 是适配器契约**：给出统一接口与配置模板，未部署外部服务；
   把「接口已定义」说成「已接入 Milvus/Neo4j」是不诚实的。
4. **训练不在本仓库执行**：`TrainingJobSpec.executed_here` 恒为 `False`；
   应用侧真实能力是「路由 / 成本 / 延迟 / 结构化输出校验 / 评测」，不是训练模型。

> 这四条写进文档，比把所有条目都标成「已实现」更有工程价值——面试与生产评审里，
> 能说清能力边界的人，比声称什么都做过的人更可信。
